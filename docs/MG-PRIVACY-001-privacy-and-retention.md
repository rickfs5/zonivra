# MG-PRIVACY-001 — Privacy, retention and deletion

Status: IMPLEMENTED (MVP 1), candidate pending independent review. Date: 2026-10-25. Applies to webcam sessions. Recorded MP4 runs use the registered video file and are outside this document.

## 1. Default and modes
- **Privacy ON is the default**: the backend (`POST /api/webcam/sessions`, field `privacy`, default `"on"`), the UI, a fresh installation, a restart and an absent preference all start in Privacy ON. The UI keeps NO stored preference: every page load starts at ON. `"off"` must be requested explicitly per session; any other value is refused (422).
- The mode is **fixed when a session starts** (`cfg.retain_frames`). Changing the selector affects only the NEXT session. The live view reports `retention` (`metadata_only` or `frames`) during capture.
- **Privacy ON**: frames are captured and used for genuine local inference; the encoded frame is dropped as soon as the detector has consumed it. No JPEG, PNG, thumbnail, video, debug image or spill file is written (the staging directory of the session is never given a `frames/` directory). The stored session has `retention.mode = "metadata_only"`, an empty evidence list and a `jpeg_sha256` of `null` for every sample.
- **Privacy OFF**: each analysed frame's exact received JPEG is written atomically to the session's staging directory and stored as evidence (`frames/NNNNNN.jpg`) with its SHA-256. Budget: `MAX_SESSION_BYTES`. The UI shows a persistent banner while frames are retained.

## 2. Metadata (retained by default, also in Privacy ON)
Session metadata, the declared source (client-declared, not authenticated), frame timestamps and sampling outcomes (analysed / dropped / stale / error), detected classes and bounding boxes, track ids and uncertainty markers, zones, risk states and events, performance statistics. A SHA-256 of the DECODED pixels (`pixel_sha256`) is kept per analysed frame; it is not recoverable to an image but allows someone who already holds a candidate image to test whether it is that frame. **Metadata is not anonymous**: positions and times of people can identify behaviour. No raw pixel is stored in JSON, logs or base64 fields (tests scan for image magic numbers and base64 JPEG/PNG prefixes under the whole test storage).

## 3. Verification and trust (what "Verificar" can say)
| Session | Verification | Result |
|---|---|---|
| Privacy OFF, frames present | deep: re-decode every stored JPEG, re-run the model, compare; rebuild manifest and provenance; re-hash the weights | may become `verified` (local integrity and local reproducibility only; never external authenticity) |
| Privacy ON (`metadata_only`) | metadata integrity only: digests, schema, sample log, manifest rebuild, the COMPLETE provenance document (its SHA-256 is part of the session identity, so a coordinated edit of `provenance.json` and `export.json` is detected), `no_frames_persisted_on_disk`. The recorded runtime environment (packages, device) cannot be re-executed without images and is NOT independently verified | `visual_verification = unavailable_no_frames`; **never `verified`**; trust stays `session` (or `unverified` after a restart) |
| Media deleted by the user (`media_deleted`) | as Privacy ON, plus the tombstone | same; any grant is removed |
A failed check of any depth removes the grant for good (monotonic revocation). `/api/events` and `/api/overview` count only sources with an intact grant as real inference; stored model-inference claims without a grant are reported in a separate `unverified` bucket. The UI never presents discarded imagery as re-verifiable.

## 4. Deletion (`POST /api/sessions/delete`, `POST /api/sessions/{id}/media/delete`)
- Needs the literal confirmation `ELIMINAR` and, for session deletion, the **exact count** the user saw (`expected_count`); a changed count is refused (409). Either an explicit id list or `all`, never both.
- Only directories that are provably stored **webcam sessions of this application** are deletable: id `session_<16 hex>`, direct child of the runs directory, not a symlink, canonical path, `source.json` of kind `webcam`, no symlink inside, one filesystem, only regular files and directories. Anything else is **refused with its reason** (never guessed). MP4 runs, simulations, source videos, weights, review archives and unrelated files are never matched.
- The session directory is renamed aside atomically and then removed; the response reports per session `deleted` / `refused` / `missing` / `failed` (residue is named). Deletion is refused while a session is being finalized.
- `media/delete` (Privacy OFF sessions only; needs `expected_files`) renames the complete validated `frames/` directory aside in one atomic step, writes `media_deleted.json` describing exactly that set (`files`, `evidence_sha256` of the historical evidence list, plus the informational `deleted_utc` and `bytes_reported`; verification rejects a tombstone whose file count or evidence digest does not match the manifest, and states that `deleted_utc` and `bytes_reported` are recorded values that cannot be verified once the files are gone, and risk/export output then reports `evidence_status: media_deleted` / `evidence_available: false` instead of live evidence links) (on failure before the tombstone the frames are put back), then removes the aside copy and reports any residue; the session then behaves as image-less. Session deletion and the installation of a finished session are serialized by one store lock, and the inode is pinned BEFORE any inspection and the renamed-aside directory must be that same inode (for media: with the same regular-file set and byte total), else it is restored and nothing is removed. A local process of the same user that can rewrite the storage directory is trusted by the threat model (§5); these checks make substitution detectable, not impossible.
- Existing personal sessions are NEVER deleted or read by the application on its own; deletion happens only through these confirmed calls. Test suites run on isolated storage and never contact a user's server (the E2E runner refuses an occupied port).

## 5. Limits MineGuard cannot control
Browser memory and caches, operating-system memory compression and swap, screenshots or recordings made by the user or other software, backups of the project directory, and copies the user exports. Deleting a session removes MineGuard's copies only; it cannot erase data already copied elsewhere. Privacy ON does not affect what the browser camera pipeline does outside MineGuard.

## 6. Added by MG-VERTICAL-02 (2026-10-25)
- **Late declaration sidecar.** After an unexpected finalization a bounded, server-judged client declaration may be stored as `late_declaration.json` inside the session directory. It holds sequence numbers and times only (no pixel), is not digest-bound, and is removed with the session by «Eliminar sesión».
- **Feeds.** A video feed persists no image. Its operator preview is the latest analysed frame of an authorized local FILE kept in memory only (`no-store`), replaced by the next and released when the feed ends. A stopped feed leaves a metadata-only summary (`runs/feeds/feedrun_*.json`, `frames_persisted:false`) that can be deleted with typed confirmation. Browser cameras are not feeds yet.
- **Alerts and dashboards** store and show metadata only; notification text never contains an image.
- Privacy ON/OFF, deletion and trust semantics of §1–§5 are unchanged.
