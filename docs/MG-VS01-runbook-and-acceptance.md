# MG-VS01 — Runbook and Acceptance Evidence (MP4 real-inference vertical slice)

Status: PROPOSED (Night Run 01; closeouts Night Run 02, Night Run 03, RC-1S). Date: 2026-10-24.
Scope of §§1-6 (HISTORICAL, VS-01): one vertical slice (MP4 → decoder → RF-DETR Nano → observations → browser review → JSON export). **Superseded 2026-10-25:** webcam, tracking, zones and the risk engine are now implemented (§4k onward and `MG-PRODUCT-001`); RTSP and multi-feed are not implemented. Where §5 and §6 say "no tracking, no zones, no risk evaluation", that was the VS-01 state.
This is a decision-support prototype; it is not a safety-critical, certified or collision-avoidance system. Detections are model output on uncalibrated video; no physical distance is stated.

## 1. Pipeline (demonstrated behavior)
`test-assets/*.mp4` → registered by SHA-256 → `decode.py` (macOS AVFoundation `AVAssetReader`, every frame, scaled by the decoder to 1280×720, per-frame PTS ticks) → every N-th frame to `detector.py` (RF-DETR Nano, weights SHA-256 verified first) → `analysis.py` (integer bbox, permille confidence, COCO → `mg.cls.v0`, evidence JPEG + RGB24 pixel SHA-256 per analyzed frame) → `runs/<run_id>/` → FastAPI → React UI.
Observation schema: `mg.obsset.vs01` (extension of the PROPOSED `mg.obsset.0.2`; JSON Schema at `backend/schemas/mg.obsset.vs01.schema.json`). `run_id = "run_" + digest16(obsset_digest)`; the digest is a SHA-256 over the canonical JSON (integers, strings, booleans, null only) of everything except `meta`.

## 3. Timestamp mapping (documented and tested)
- Frame table: decoder PTS ticks, time base `1/timescale` (1/30000 for the clip), frame 0 = 0 µs. `pts_us(i) = round_div((ticks[i] − ticks[0]) · num · 10⁶, den)`, never accumulated (`timebase.py`; vectors from MG-DATA-001 §4 are tests).
- Frame `i` covers `[pts_us(i), pts_us(i+1))`; the UI maps the browser's presented `mediaTime` to a frame with the same rule (`frameForTimeUs`, tested) and seeks to `pts_us(i) + 0.5 ms`.
- A frame that was not analyzed is labeled as such; the overlay of the last analyzed frame is drawn dashed with an explicit notice.
- Browser playback is not claimed to be frame-perfect. What is demonstrated: after a seek to `pts_us(300)+0.5 ms` the UI reported frame 300 in headless Chrome, and the overlay edge pixel lies at the recorded bbox position.
- Coordinates are in the 1280×720 analysis frame (`image_px_v1`); the native video is 3840×2160 (the decoder scales).

## 4a. Validation codes
MG-DATA-001 codes implemented: V-01..V-11, V-17, V-20 (V-12..V-16, V-18, V-19 belong to zones, policy and the risk engine and are not implemented). VS-01 extension codes (not in MG-DATA-001): V-21 `params_hash` does not match `producer.params`; V-22 a digest field is not 64 lowercase hex characters; V-23 detector class id/label/taxonomy or `label_map_digest` inconsistent with the COCO map; V-26 `frames` are not strictly increasing by `frame_index` (MG-DATA-001-005: never sorted into shape, never duplicated; deep verification additionally requires the manifest evidence to list the same indexes in the same order, check `frame_order_canonical`); V-17 (extended) a string **or an object member name** anywhere in the document, `meta` included, is not Unicode NFC (MG-DATA-001-006): rejected, never silently normalized (`canonical_bytes`, the strict loader and the import endpoint all refuse a decomposed `e\u0301` key while accepting the composed `\u00e9`); V-25 an input contains a duplicate object key at any depth or a non-finite number (CJ-1; import bodies and every stored artifact are parsed strictly, before any framework deserialization can collapse the duplicate); V-24 a `model_inference` set has no analyzed frame, or its analyzed frames are not exactly the frames the declared `producer.params.stride` selects, or a status range other than `not_analyzed_stride`.
V-11 is applied to the whole document: every key at every depth, `meta` and `producer.params` included, normalised with NFKC, case-folded and trimmed before matching `distance*`, `speed*`, `ttc*`, `collision*`, `*_m`, `*_km`, `*_kmh`, `*_mps`; it runs before structural validation so a forbidden field is reported (with V-20) even in an otherwise malformed set. `meta` is a strict schema (creation time, tool, notes, provenance_id, elapsed_ms, dropped_degenerate_boxes); other keys give V-20. Adversarial fixtures: `test_schema_validation.py` (V-11 and meta tests). V-09 for `model_inference` requires the exact adapter/model/weights tuple from `models/MANIFEST.json`.
Run integrity and trust: shallow verification (`?deep=false`) checks that `export.json` equals its component documents, the digests, the schema, the evidence file hashes, the evidence-to-observation pixel hashes and the weights hash; it reports `deep: false` and states that pixels, timestamps and model output were not re-checked. **Deep verification** (the default, used by the UI) additionally checks that the registered source file is byte-identical to the analyzed one (`source_file_sha256_matches_binding`), re-decodes it, compares every analyzed frame's pixel hash and the frame table, **re-runs RF-DETR on every analyzed frame and requires the integerized boxes to equal the stored observations exactly**, requires that at least one model call was made and that the number of calls equals the number of analyzed frames (`model_invoked_on_every_analyzed_frame`), applies the evidence rendering contract (§4b), and compares stored claims with values obtained from the executing environment (§4d): `executing_model_matches_stored_claims`, `params_match_executing_environment`, `provenance_equals_executing_environment`, `source_document_equals_decoder_output`, `source_binding_equals_decoder_output`, `manifest_equals_decoder_derived_record`. Shallow verification also checks that evidence paths are exactly `frames/<index>.jpg`, unique, non-symlink, and the only files in `frames/` (`evidence_paths_canonical`). It fails closed: a missing source video, an unloadable model, or an incomplete run directory yields `ok: false`.
Trust states returned with every run (`trust`): `session` (created by this server process), `verified` (passed deep verification in this process), `unverified` (found on disk; for example after a restart or a copied or planted directory). The UI states «real inference» only for `session` and `verified` runs; for an `unverified` run it labels the origin as a stored, NOT verified claim (it never shows the real-inference label) and draws its boxes only as a provisional inspection view (grey, dotted, every label prefixed «SIN VERIFICAR», table headed «vista provisional, NO verificadas») (MG-ORIGIN-002). The four observation sources have four distinct labels: verified local inference, unverified stored model-inference claim, synthetic scripted replay, human annotation. Trust is in memory only. The grant stores a fingerprint of `observations.json`, `export.json`, the registered source MP4 (re-hashed in full, not stat-cached) and every evidence JPEG named by the manifest (re-hashed); it is recomputed on every read of the trust state, and any change, replacement or removal gives `unverified`. Revocation is monotonic: a mismatch seen by any read, or ANY failed verification (deep or shallow, of a run or a session), removes the grant for good; restoring the bytes identically does NOT bring it back, and only a later successful deep verification grants `verified` again (sessions stored without images can never be deep-verified, so they stay `unverified` after a revocation). The video endpoint re-hashes the file against its registered SHA-256 and answers 409 on mismatch (404 if removed); the frame endpoint answers 409 when a JPEG differs from the manifest hash or from the hash pinned at grant time, and 404 for symlinks. Deep verification also fingerprints before and after, and refuses to grant trust if anything changed while it ran. A run found on disk that was never verified in this process is `unverified` and its evidence is served with that label. The export and bundle endpoints refuse (409) a run whose `export.json` differs from its components. Importing an `origin=model_inference` set requires a run directory that passes deep verification; `replay` sets are labeled replay and are never promoted.
Limit of this check: re-inference equality was observed on one machine (Apple M4 Pro, `mps`) across several runs and restarts; it is not claimed to hold across hardware or runtime versions, where a legitimate run could fail deep verification. A party with write access to the run files, the model weights, `models/MANIFEST.json` and `backend/mineguard/detector.py` together could still forge a run that verifies; the weights hash is pinned in tracked source and in the manifest, not in a signed or external trust root. Deep verification also requires the stored provenance to equal the canonical model record and the current runtime.
Track semantics (V-08) are deferred: VS-01 has no tracker, so `tracks` must be empty.

## 4b. Evidence rendering contract (`mg.evidence.jpeg_q90_v1`)
The evidence image is a lossy rendering (Pillow JPEG, quality 90, 1280×720, RGB, no resizing) of the decoded RGB frame that was given to the model. Byte or pixel equality between the JPEG and the decoded frame is **not** claimed. The binding of the processed pixels is the `pixel_sha256` of the RGB24 buffer, which deep verification recomputes from the re-decoded video. For the displayed JPEG, deep verification decodes the stored file and requires, against the re-decoded frame: format JPEG and shape 720×1280×3; mean absolute error ≤ 4.0 levels; PSNR ≥ 34 dB; and no 16×16 tile with mean absolute error above 14 levels. Measured on this clip at stride 37 (21 frames): PSNR ≥ 39.0 dB, mean error ≤ 2.1, worst tile 6.7. The constants live in `analysis.EVIDENCE_CONTRACT` and are copied into the manifest as `evidence_contract` for documentation; verification uses the code constants, not the manifest.
What this detects: substitution of an evidence image by another picture and edits that change a 16×16 tile by more than 14 levels on average (`test_consistent_evidence_swap_*`, `test_localized_edit_*`, with the manifest hash and `export.json` rewritten to be self-consistent). What it does not detect: edits smaller than that tolerance, or a JPEG that differs from the source in ways below the tolerance. A different libjpeg or Pillow version could change the rendering slightly; the tolerance, not byte equality, is what makes legitimate runs verify.

## 4d. Trust boundary: what verification does and does not establish (Night Run 03; owner decision AP-33)
RC-1 is a local experimental research application. Three different things must not be confused:
| Level | What it means here | Provided? |
|---|---|---|
| **Local integrity** | The run's files agree with each other and with the bytes on this machine: digests, schema, evidence hashes, `export.json` equals its components, the registered source file and every evidence image are byte-identical to what was analyzed. | Yes |
| **Local reproduction of inference** | On this machine, now, the source is decoded again by the macOS decoder and RF-DETR Nano is run again on every analyzed frame; the boxes equal the stored ones exactly, and the media facts, time base, timestamps, device, resolution, model record and package versions equal what this process measures or loads. | Yes (deep verification only; a run made in another environment fails and must be re-analyzed) |
| **Independent external authenticity** | A third party who does not control this machine can rely on the run being genuine. | **No.** |
Why not: every input to the verification is a local file or a local process. Someone who controls the machine can edit the run directory, `models/MANIFEST.json`, `detector.APPROVED_MODEL`, the weights and the verification code together (or replace the weights with another checkpoint under the same name, re-run the analysis and obtain a run that verifies). The approved-model record in tracked source makes such a change visible in git; it does not prevent it. Preventing it needs signing, an external trust root or attestation, which the owner has explicitly not authorized (no PKI, trust services, remote signing, secrets management or cloud). MG-RC1-009 is therefore a **deferred architectural requirement, not a fixed defect**.
Wording rules that follow: the API's `verified`/`session` trust states mean "locally verified / created by this process", every verification report carries `trust_scope` (`local_integrity`, `inference_reproduced_locally`, `external_authenticity: false`), and the UI states the scope next to the trusted banner. A run must not be described as authentic, signed, certified or independently verified. An exported file that is moved to another machine carries no authenticity guarantee beyond the hashes it contains.

## 4f. Local API security baseline (RC-1S, MG-SEC-002)
Implemented in `backend/mineguard/security.py` (pure ASGI middleware, no third-party identity, cloud or multi-user component) and wired in `create_app`.
| Control | Behavior | What it stops |
|---|---|---|
| Loopback only | Launch scripts bind `--host 127.0.0.1` (a test fails if any script binds anything else); the middleware also refuses any request whose peer address is not `127.0.0.1` / `::1` (403) | access from another machine, even if the bind were widened by mistake |
| Host allowlist | `Host` must be exactly one header whose host part is `127.0.0.1` or `localhost` (port ignored, `[::1]`, `0.0.0.0`, LAN addresses, look-alike names, userinfo tricks refused) → 403 | DNS rebinding: the attacker's name arrives in `Host` although the socket is loopback; the token is never handed out to such a request |
| Origin | an `Origin` header, if present, must equal the request's own origin (`http://<Host header>`), otherwise 403; `null`, other ports, `https`, duplicates refused; `Sec-Fetch-Site` of `cross-site` or `same-site` refused | cross-site fetch/form posts from any browser tab, including preflight (`OPTIONS` from another origin gets 403); no `Access-Control-*` header is ever emitted, so CORS is never opened |
| Session token | a fresh random 256-bit-class token per server process; every `/api/*` call except `/api/health` needs it: header `X-MG-Token` for any method, or the `mg_session` cookie for GET/HEAD only (media, image and download elements cannot set headers) → 401 otherwise; never accepted in a URL; constant-time comparison | unauthenticated local processes and pages; CSRF (a cookie is attached automatically by browsers, so it can never authorize POST) |

## 4h. Decoder memory leak found and fixed during RC-1S
Symptom (Night Run 02-03 and the first RC-1S gate): repeated system memory exhaustion, swap growing by tens of GB within a minute while the test process itself stayed near 1.1 GB; two background runs were stopped by the harness and one by the resource guard.
Cause (measured, not inferred): `AVAssetReaderTrackOutput.copyNextSampleBuffer()` returns a +1 `CMSampleBufferRef` that PyObjC does not release for this Core Foundation type (retain count 2 with one Python proxy). The system decoder service `VTDecoderXPCService` therefore kept every decoded frame (~3.5 MB each, about 2.7 GB per pass over the 742-frame clip) until the client process exited; memory was attributed to that service, not to the Python process, so process-footprint monitoring could not see it. Each deep verification or analysis is one pass, so `test_rc1_closeout.py` (about fifteen passes) pushed the service past 24 GB.
Fix (`decode.iter_frames`): each frame is handled inside an autorelease pool, the +1 reference is balanced with one `CFRelease`, and all Core Media references are dropped before the frame is yielded. After the fix the service stays at 0 MB over a full pass (it reached 2.7 GB before), `test_rc1_closeout.py` ran with 0 MB of swap growth, and pixel digests and run ids are unchanged (the gate re-checks the identical run id). Regression test: `test_decoder_does_not_leak_decoded_frames_into_the_system_decoder_service`.
Residual: the fix relies on PyObjC's reference behavior for `CMSampleBufferRef`; a PyObjC release that changes it would double-release (crash) and the regression test plus the video tests would show it immediately.
