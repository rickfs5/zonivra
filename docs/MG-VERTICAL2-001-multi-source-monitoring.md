## 2. Source architecture
A **feed** is one independently controlled analysis of one source. Identity: `feed_<8 hex>`; each run gets its own `run_uid`, so the event ids of two runs of one feed never collide.
- Implemented source: `mp4_file` — a registered local MP4 (`test-assets/*.mp4`, decoded by the macOS system decoder). Every feed carries `source = {kind, video_id, filename, sha256_prefix, repeated_source, provenance, physical_camera:false}`.
- `repeated_source` / provenance (corrected in cycles 26-28; this paragraph replaces the earlier «frozen at start» text, which is obsolete): four facts are kept apart. (1) **Launch provenance** (`launch_repeated`) is immutable for a run: was the file already played by another feed when the run started. (2) **Evidentiary provenance** (`source.provenance`: events, alerts, dashboard aggregates, saved summary) is sticky: once another ACTIVE feed played the same file at any moment of the run, the whole run is `repeated_source_simulation` and is never reclassified as genuine from the present state; every feed involved is labelled, and alerts of the earlier feed's run are re-labelled (monotonic). (3) **Present relationship** (`shared_now`) goes back to «alone» when the other feed stops. (4) **Overlap history** (`overlap`: `launch_repeated`, `intervals[{from_after_us, until_before_us}]`, evidence `sample_time_bounds`) records WHEN the overlap was present, in source time and bounded by sample times (not exact instants); each event and alert carries a derived `overlap_phase` (`alone`, `from_launch`, `before_overlap`, `during_overlap`, `between_overlaps`, `after_overlap`, `unknown`, and `mixed` for an alert that merged episodes of different phases) so the period before the overlap stays distinguishable although the run-level label is conservative. A record without interval evidence (a summary or alert saved by an older version) is `unknown` when it was repeated and `alone` when it never was. Restarting a feed is a new run with a fresh history. This is a **concurrency simulation, never several cameras**; the UI, the alerts, the dashboards and the saved summaries repeat that label, and the events of repeated sources are counted apart from real ones. Limits: at most 64 disjoint intervals are kept per run — beyond that `overlap.truncated` is set and later episodes are `unknown` (MG-PROV-029); interval bounds are sample times; an overlap that ends while the feed is paused is found at its next sample; no phase is assigned to a scripted simulation.
- Reserved interface: `browser_camera` (several browser devices). It is architecture only: creating such a feed answers 501 `mg.refusal.feed_source_not_available`. Activating it needs a human-executed browser-permission test and a physical-camera acceptance that does not exist yet.
- Source time: every sample is stamped with the source's own presentation time (relative to the feed start, strictly increasing also across loop passes), never the scheduling time. Risk results are therefore deterministic with respect to the source and independent of the scheduler's jitter.
- Sampling: one decoded frame per `1/sample_fps` of source time is offered (0.2 – 10 /s); the rest are `skipped_by_sampling`, an intentional omission that is counted and never reported as loss.

## 3. Scheduler and bounded concurrency (ADR 0005)
```
reader thread / feed ─► bounded queue (2) / feed ─► scheduler (1 thread, least-recently-served first) ─► ONE RF-DETR Nano ─► commit under the feed lock ─► that feed's tracker, zone engines, kernel ─► alert engine
```
- ONE model instance and ONE inference thread for every feed (the model is never instantiated per feed). The scheduler picks, among feeds with a waiting frame, the one served longest ago; equal workloads receive equal service (MEASURED, §13).
- Queues hold at most 2 frames per feed. Two modes: `realtime` (paced by the source clock × speed; overload drops the OLDEST queued frame and is counted `dropped_queue_overflow`) and `throttled` (backpressure: the file waits for the model; nothing is dropped, playback slows).
- Staleness: a decoded frame older than 3 s (wall clock) **at the commit** is rejected and recorded `dropped_stale`. The check is made under the feed lock immediately before the sample becomes the current observation. The model's cold start is not counted: readers offer nothing until the shared model is loaded (the panel says «Cargando el modelo»).
- Order: decided samples are fed to the tracker and the kernel strictly in source order (dropped samples included, as not-analysed → UNKNOWN), so no dwell or hold continues silently across a drop.
- Isolation: tracker, zone engines, counters, queue, events and failure state are per feed; tracker ids are namespaced `feed_x/T1`; a failing source ends only that feed (`failed`, explicit reason, the others continue); a detector error on one frame is an `adapter_error` sample of that feed only; an UNEXPECTED internal error while a feed is processed ends that feed explicitly (`failed`, reason `internal_error`, queue drained, summary saved). The consumption of one sample is TRANSACTIONAL (cycle-24 MG-FEED-024, remediation UNREVIEWED): before a sample is applied, the tracker and every zone engine of the feed take a checkpoint of the state a sample can change (the small live state is copied, the long histories are only measured); if anything fails midway they return to exactly their pre-sample state (verified by randomized checkpoint/rollback equality tests, not by inspection), the frame is moved ONCE from `analyzed` to `dropped_stopped` (reason `internal_error`) and each undecided queued frame is counted once, so `offered` equals the sum of the outcomes; publication to the alert engine happens only after the commit and is not itself rolled back. The rollback covers the tracker, the zone engines and the feed counters, not an external effect that a failing publication might already have had. The other feeds go on, an error inside the scheduler loop never kills the only inference thread, and the shared model lock is released in every case; tracks the tracker ended by an ambiguous association reach the kernel as identity breaks (the episode closes as `track_discontinuity`) and are counted per feed (`discontinuities`: a measured count, zero only where nothing broke). A source that fails **before its first frame** (for example the system decoder refusing a concurrent start; observed once in five 3-feed starts) is retried up to 3 times (0.4 s apart) and the retries are shown; a failure after the first frame is not retried. If the model cannot be loaded every feed ends `failed`/`model_unavailable` and the shared lock is released.
- Exclusivity: running feeds hold the same model lock as MP4 analysis, deep verification and webcam sessions. While a feed plays, those answer 409 `job_in_progress` (and the reverse). The lock is released when the last feed stops or ends.
- Controls: start, pause, resume, stop and independent restart (a new run of the same feed and zones), per feed; `stop` discards that feed's queued frames and records them `feed_stopped`. A stop requested by the operator is always reported as `operator_stop`.
- Zones: per feed, edited with compare-and-swap (`expected_revision`, 409 on a stale write). A running feed may be edited: the old zone engines are finished at the last sample and their events are kept (`closed_by: zone_edit`, right-censored); the new engines start fresh with their own event ids, while the RUN identity (alert source, saved summary) does not change, so the alerts of the old episodes close normally and no twin alert appears. The operator's drawn polygon is kept until the server accepted the save; a conflict or failure shows its reason and the retry uses the refreshed revision.
- Capacity: at most 5 feeds exist (hard cap); the default active limit is 3, which is the validated count. Raising it to 4 or 5 needs an explicit acknowledgement («no validado») in the UI/API.

## 4. Webcam heartbeat and temporal accounting (MG-WCAM-019 / 020 / 021)
### 4.1 Lifecycle messages (019)
- Control messages — heartbeats AND stops, for live sessions and finished ones — are numbered (`X-MG-Msg-Seq`, 0…2·10⁹) and acknowledged (`ack` in the answer). ONE entry point (`SessionManager.control`) keeps the cache: a retried message (same number, same payload) returns the **original answer** with `duplicate: true` and changes nothing (also after the session became a tombstone, and for a late declaration: no second sidecar entry); the same number with a **different payload is refused** (409 `control_message_conflict`); a number lower than one already seen is flagged `reordered` (a cumulative watermark can never be lowered; a stop is terminal). The last 64 numbers per session are remembered and released with the session; errors are never cached, so a retryable 503 can be retried with the same number. The one-time trust grant of a stop is never replayed.
- Client (`lifecycle.ts`, `WebcamPanel.tsx`): one heartbeat in flight at ~1 Hz, cumulative (a lost one is superseded by the next; one quick retry); the **stop** is retried at most 5 times with 0.3/0.6/1.2/2.4 s back-off (≤ 4.5 s), always with the same message number, and a retryable 503 (the model is still inside a frame) keeps the session and is retried until a WALL-CLOCK deadline of two minutes (`lifecycle.ts retryBusy`): every such answer comes from the server after at most 5 s (`WORKER_JOIN_S`), so a permanently blocked detector ends the client's retries after about two minutes plus one server wait, never after a number of attempts times a long wait. Each stop request receives an `AbortSignal` and a timer sized to the time that is LEFT of the deadline: a request that never settles is aborted (a `fetch` honours the signal) and abandoned at the deadline (`StopDeadlineExceeded`, message id `mg.client.stop_deadline`), so the total is the deadline plus at most one pause (cycle-24 MG-LIFE-024, remediation UNREVIEWED). After that the server may still hold the session open; it finalizes it by itself. The vectors use a virtual clock and a short real-clock deadline; they do not exercise a real stalled socket. Leaving the area or closing/reloading the tab sends one best-effort keep-alive stop (no loop can outlive the page). No unbounded queue and no unlimited retry exist.
- Clean stop vs disappearance: a stop carries the final sequence (`X-MG-Next-Seq`) and the close reason `client_stop`/`device_ended`; a client that falls silent for 15 s is finalized by the server as `client_disconnected` (right-censored). The accounting records `closure: clean_stop | device_ended | unexpected_disconnect`.
- **Bounded late declaration.** After an *unexpected* finalization the server still admits a loss declaration for `ADDENDUM_WINDOW_S = 300 s`, only when ALL hold: the session closed as `client_disconnected` (a clean stop is final); the window is open (server-measured); the declaration is plausible (no more ticks than the time since the last accepted frame allows at the declared cadence, +2); it is monotonic and not older than the last accepted frame; at most 8 are kept. It is written as the sidecar `late_declaration.json` in the session directory with `digest_bound:false`; **no digest-bound document is rewritten**, the stored counters and accounting keep their honest limit, and verification checks the sidecar's form but never lets it change the identity or the trust state. Everything else is refused with a stated reason and the interval stays *unobserved, exact count unknown*.
- Maximum reconciliation interval: 15 s (idle detection) + 300 s (window) = **315 s after the last accepted frame**. Reason: a reload, a laptop sleep or a Wi-Fi roam normally returns within minutes; after five minutes the browser state that issued the ticks is gone and a declaration could no longer be told from a guess. The window is memory-based (tombstones): a server restart closes it.
- If the client never comes back nothing is invented: `tail_basis = none_right_censored`, `tail_exact = false`, the tail length is *not known*, and the zone state after the last sample is UNKNOWN by the kernel's own right-censoring.
### 4.2 Commit-time freshness (020)
A frame becomes the current observation only inside one critical section under the session lock that (a) re-checks the 2 s age bound, (b) renames the spooled JPEG to its evidence name (Privacy OFF only), (c) records the analysed sample, its objects and pixel hash, and (d) feeds the tracker and the kernel. A result that expired while being queued, inferred, spooled or while the worker waited for the lock is recorded `stale`, its temporary JPEG is deleted, and nothing of it enters the tracker, the kernel or the live view. Privacy ON never writes a file at all.
### 4.3 Coverage accounting (021)
- Every capture tick consumes a sequence number. Time model: the first accepted frame defines the session clock at `seq × declared cadence` (an **extrapolation**, flagged `origin_basis: cadence_extrapolation`; `measured` when the session starts at sequence 0); real frames keep their measured spacing.
- A missing **prefix** (first accepted sequence > 0) is one unknown stub at time 0; an interior **gap** starts one declared cadence interval after the last observation (that observation stays valid for one interval) and lasts until the next sample; a **tail** declared by a stop or a heartbeat covers `lost × cadence` (the declared extent, not one invented short stub) and the session's end moves accordingly.
- `live_stats.accounting` (digest-bound and re-derived by the verifier): `captured_declared` (client declaration or null), `submitted` (sequence-bearing requests that reached the server and were examined: accepted + refused at intake + refused at the transport), `accepted`, `analyzed`, `dropped`, `adapter_error`, `unknown_intervals`, `tail_basis`, `tail_exact`, `closure`, and the split of the ticks that produced no accepted frame: `prefix_frames + gap_frames + tail_frames = never_observed_frames + rejected_invalid_frames + unclassified_frames`. Every sequence-bearing request that REACHED the server and was not accepted — refused at the transport (not a JPEG, wrong size, oversize) or at intake (late/non-monotonic, over a limit) — leaves the interval UNKNOWN (nothing was analysed) but is recorded in a bounded INTERVAL LEDGER (sorted disjoint ranges, at most 4 096 islands; consecutive refusals share one range) and counted as `rejected_invalid_frames` instead of `never_observed_frames` (client-side loss). Gaps are reconciled from the ledger when the session closes and in the live view, so a frame that arrives AFTER a later one (two uploads may be in flight) is counted as examined, not as lost (cycle-24 MG-WCAM-024, remediation UNREVIEWED). When the ledger has no room the remainder is reported as `unclassified_frames` (at most the unrecorded count, only inside their sequence envelope): it can over-state the uncertainty, never hide it, and it is never relabelled as never observed. The verifier re-derives the split (`rejected_invalid_frames + unclassified_frames` cannot exceed the refusals counted; per stub, examined + unclassified cannot exceed the ticks it stands for). The sequence number is read before the payload is judged and each unknown stub carries `rejected_frames` and `unclassified_frames`. Sessions stored before this split keep their older accounting shape and still verify. The check `coverage_accounting_matches_the_sample_log` recomputes everything the log can prove; the capture count and the tail basis stay client declarations and are labelled so.

## 5. Privacy and retention (unchanged contract, extended)
- Privacy ON is the default everywhere and fixed per capture session; no frame, thumbnail or pixel is persisted. Privacy OFF is an explicit per-session opt-in, shown in the UI, with «Eliminar imágenes» and «Eliminar sesiones» (exact confirmation, exact count, atomic scoped deletion, symlink and traversal defences) exactly as before. The new sidecar is deleted with its session.
- Feeds persist **nothing visual**: a stopped or ended feed writes `runs/feeds/feedrun_<16 hex>.json` — counters, latency, event list, zone digests, producer versions — marked `trust: live_summary`, `retention.frames_persisted: false`. It can be listed and deleted (`POST /api/feeds/history/delete`, `ELIMINAR` + exact count, regular files only). `runs/feeds`, `runs/alerts` and a session directory receiving a late declaration are opened once without following symlinks, checked to be real directories owned by the user, and every read, write, rename and unlink is relative to that open descriptor (`safedir.py`): a symlinked or swapped directory is refused (reported as `store_status: unsafe`) and nothing outside MineGuard's storage is read, written or deleted. It cannot be re-verified from images. Like a session, a saved summary is `live_summary` only while THIS process holds its grant (it wrote exactly those bytes); after a restart, an edit or a planted file it is listed as `unverified`, validated for exact members, closed vocabularies, finite ranged numbers, non-negative latencies and counters and bounded key lengths (cycle-24 MG-STORE-024, remediation UNREVIEWED) and never counted as real history. Writes use an unpredictable exclusive temporary name inside the pinned directory, so a pre-created link (symbolic or hard) is never written through.
- The operator preview of a file feed is the latest analysed frame of the **authorized clip**, held in memory only, served with `Cache-Control: no-store`, replaced by the next one and released when the feed ends; it is never written. No personal webcam image is part of any feed.
- Alerts persist metadata only (`runs/alerts/alerts.json`, `settings.json`): no pixel. Notification titles and bodies contain the label and the zone, never an image.
- Dashboards expose counters and OS measurements only; tests assert that no image bytes, token or environment value appears in them.

## 6. Risk rules and uncertainty
Unchanged: kernel `mg-risk-kernel/2.0.3` (2.0.1 plus the MG-RISK-028 silence closure, MG-RISK-002 section 10) (R1 RED = person ∧ vehicle in the same zone; R2 YELLOW = person dwelling with no vehicle), tracker `0.3.0` (ambiguity endings are delivered to the kernel as identity breaks; counted as `tracking_discontinuities`; a stored evaluation made by tracker 0.2.0 is reported as «not compared», never as failed), MG-RISK-002. UNKNOWN (not observed / not analysable) is never GREEN and never an emergency: it is shown as a low-priority **diagnostic** and in the dashboards as «sin observar».

## 7. Events and alerts
Chain: kernel event → alert policy → alert record → dispatcher → delivery status.
- Record (`mg.alert.v1`): `alert_id`, `kind` (`risk_event` | `diagnostic`), `event_id`, `feed_id`, `zone_id`, `severity` (RED | YELLOW | UNKNOWN), `priority` (high | warning | diagnostic), `created_utc`, `source{source_id, kind, label, provenance, repeated_source, incident_class, physical_camera}`, `status`, `acknowledged_utc`, `resolved_utc`, `resolved_by`, `occurrences`, `suppressed_count`, `delivery{in_app, browser, sound}`, `delivery_state`, `simulation`, `rev`; `occurrences` are `{event_id, open, source_id}`. The in-app channel is `stored` when the alert is recorded and becomes `displayed` only when the operator view reports it (seen, acknowledged or resolved): the dashboard counts stored and displayed separately and never assumes a delivery. Records read back from disk are validated down to every nested record (exact members, vocabularies, bounds, provenance invariants, content-bound ids), including the optional bookkeeping members (`reopened_count` an integer 0…10⁹, `pinned_open` and `loaded_from_store` booleans, each occurrence's `source_id` a non-empty string ≤ 120; records written before cycle 24 have occurrences without it and are shown with `source_id: null`), and the projection rebuilds them as exact primitives (cycle-24 MG-STORE-024, remediation UNREVIEWED); they are returned only through a projection, flagged `loaded_from_store` (the alert center shows «restaurada del disco, sin verificar»), closed when their live source cannot exist any more, excluded from the per-provenance counts and from every delivery count (`summary.by_delivery_state` included), and counted apart as «restored, unverified».
- Lifecycle: `new` (created, not yet displayed) → `active` (displayed in the alert center) → `acknowledged` (explicit operator act) → `resolved` (automatically when its episode closes, when the source closes, or by the operator; terminal). `delivery_state` is separate: `pending` | `delivered` | `in_app_only` | `failed` (**«Entrega fallida»**). It is never assumed (MG-ALERT-029): `failed` if any client channel failed; `pending` while an enabled client channel has not reported or while an alert that reached no client channel has not yet been displayed by the operator view; `in_app_only` when a client channel was denied or unsupported, or when no client channel delivered and the alert has been displayed; `delivered` only when a client channel reported delivery. Alerts are idempotent per (source, zone, event).
- Restored records (MG-ALERT-031, MG-QUARANTINE-032): a record read back from disk is accepted only if `delivery_state` equals the state derived from its recorded channel outcomes and each outcome carries the timestamp its status implies; otherwise it is refused, counted (`rejected_on_load`) and never shown as delivered. When a store is not accepted as it stands (unparseable, foreign schema, or any rejected row) the EXACT original bytes of `alerts.json` are first kept in `alerts.rejected.<sha256 of those bytes>.json` (created exclusively through a temporary file and a hard link, so it never replaces an earlier record and a partial file never carries the final name, then read back; `preserved_rejected_store.complete` is true only after the read-back matched). The usable records are recovered separately in the rewritten `alerts.json`. A restored alert accepts no delivery report.
- Delivery reports (MG-ALERT-032): a repeated report with the SAME terminal status is idempotent (no new timestamp, detail, revision or write); a different status for a reported channel is refused (`409 already_reported`).
- RED: high priority, in-app + browser notification + sound by default (cooldown 10 s). YELLOW: warning, in-app + browser (no sound by default; cooldown 60 s). UNKNOWN: appears only after 10 s of source time without observation, in-app only, cooldown 120 s, resolves when the state leaves UNKNOWN or the source closes. All values are configurable (0–3600 s) in «Configuración».
- Storm control: same-group events inside the cooldown are **merged** into the open alert (counted, no new notification) ONLY when they are the same kind of thing — same source kind, same provenance and simulation status and, for a feed, the same RUN; a restarted feed (a new run, possibly with another provenance) is never folded into the alert of its previous run. If the merged alert had been resolved (flapping inside one run) it is reopened. The group of a feed is the feed, of a browser camera its device label (reconnections do not multiply alerts; cycle-24 MG-ALERT-024, remediation UNREVIEWED: the merged alert keeps the FIRST session as its `source`, every occurrence carries the `source_id` of its own session, a suppressed UNKNOWN diagnostic of another source leaves one bounded attributable occurrence per episode, the list holds 20 entries and **a full alert stops merging: the next episode or diagnostic starts a NEW alert, so no merged episode is only counted** (review 25 MG-ALERT-024, remediation UNREVIEWED), and a diagnostic whose carrier alert no longer exists is raised as a new alert instead of being dropped), of a simulation each press (a counter and a nonce make two presses in the same millisecond two drills). Observation of an unchanged episode changes nothing. Capacity (explicit, never silent): up to 500 alerts are kept; at that limit the oldest RESOLVED alerts are removed first, then the oldest open scripted DRILLS (source kind `simulation`; at most 50 stay open and each press beyond that retires the oldest); every other alert — including a repeated-source kernel alert, which is flagged simulation but is genuine kernel output — is never removed to make room. Between 500 and the hard ceiling of 1000 genuine alerts are still stored (the dashboard shows the state as degraded); at 1000 a new alert is **refused and counted** (`overflow_dropped`) and the operator panel says so. An alert resolves only when **every** episode merged into it has closed (open episodes are tracked independently of the 20-entry history; beyond 200 simultaneous open episodes the alert is pinned open until its source closes). After a server restart the alerts of live sources are closed with `server_restart` (their source can no longer confirm anything); drills stay open for the operator.
- Synthetic and repeated sources: alerts carry `simulation:true` and the label SIMULACIÓN / FUENTE REPETIDA; they never turn the header badge red, are counted apart (`by_provenance`) and are never described as genuine incidents. Every feed alert is `incident_class: scenario_file` (a replayed recording); a browser-camera alert would be `live_camera_declared_by_client` (the origin is declared by the client and not verified by the server).
- The scripted RED drill (`Simulaciones`) creates drill alerts that stay open until acknowledged or resolved; each press is a new, distinct drill.
## 8. Browser notification and sound
Both are executed by the browser, with the user's consent, and the server only records what the browser reports (`POST /api/alerts/{id}/delivery`: `delivered` | `denied` | `failed` | `unsupported`; a reported outcome cannot be rewritten; a channel disabled by policy cannot be claimed). Consent is per browser, starts OFF, and is kept only in that browser's local storage (the page works if storage is blocked). «Activar notificaciones» asks for the permission explicitly; a denial is recorded per alert and the in-app delivery stands. Sound needs a user gesture («Activar sonido de alerta») and plays a short tone only for eligible alerts. An alert whose channel is still waiting for consent stays `pending`; nothing is assumed.

## 10. Operator dashboard («Resumen» and «Estadísticas»)
Active feeds and the limit; risk state per feed with its zones and the «sin observar» zones; processing health (worker, model loaded, failed feeds, resources); **four numbers that are never added**: per-frame detections, unique tracks, risk events (live, repeated-source, saved history from this process, saved history unverified), notification deliveries (stored in the alert center, displayed to the operator, delivered to the browser, with sound, failed); events per source; open/acknowledged alerts by severity and provenance; the 20 most recent alerts; session retention (frames / metadata only / images deleted); a trend of alerts per interval for 15 min – 24 h (an empty window says so and draws nothing; the RED/YELLOW/UNKNOWN series count GENUINE LIVE alerts only — simulated and restored-from-disk alerts are reported apart as `simulated` / `restored` and never drawn as incidents; review 25 MG-TREND-025, remediation UNREVIEWED); the risk shown for a feed is its CURRENT state only while the feed is playing: a paused, ended, stopped, idle or failed feed is UNKNOWN and its last value is reported apart as `last_observed_risk` (review 25 MG-STATE-025, remediation UNREVIEWED).
