## 4. Risk and honesty rules enforced in the UI
`currentRisk()` (`lib.ts`) returns UNKNOWN for every feed that is not PLAYING (paused, ended, stopped, idle, failed): a last value is history and is shown apart as «último estado observado … (histórico)»; the backend operator overview applies the same rule (`risk` / `last_observed_risk`). Incident lists never show a record restored from disk as real inference (`incidentProvenance`), the alert trend counts genuine live alerts only (simulated and restored are counted apart), and every JSON body of the API is refused before parsing above 64 KiB and rejects unknown members (review 25; these corrections are UNREVIEWED). Unknown is hatched and always worded (never colour alone). Provenance tags (INFERENCIA REAL / SIMULACIÓN / FUENTE REPETIDA / SIN VERIFICAR / ANOTACIÓN HUMANA) accompany every incident and source. Event state, alert state and delivery state are different sections. No metric, class, evidence image or integration is invented; unknown values read «no medido» or DESCONOCIDO.

## 7. MG-PRODUCT-VERTICAL-04 additions (Status: candidate, 2026-10-26)
Scope: operational integration of the console with the existing core. No new model, scheduler, dependency or storage format.

**Source state vs risk state (CONFIRMED by tests).** Every feed view now carries independent fields: `state` (transport lifecycle), `risk_current` / `risk_state` (CURRENT risk), `last_observed_risk` (history), `unknown_reason` (a message id) and `observation` (`fresh`, `age_ms`, `stale_after_ms`). A feed is UNKNOWN, with a reason, when it is idle, paused, stopped, ended, failed, has no analysed sample yet (`mg.unknown.no_sample_yet`) or its newest analysed sample is older than 8 s (`mg.unknown.stale`). When the feed is observed and fresh but the risk kernel itself returns UNKNOWN for the latest sample, the reason is `mg.unknown.insufficient`. A restart (`Feed.reset`) clears `last_observed_risk`. The UI shows «Estado de la fuente» and «Riesgo actual» as two separate labels, explains every UNKNOWN in Spanish, and shows the last observed value apart as «histórico».
**Build identity (CONFIRMED).** `GET /api/build` (`backend/mineguard/buildinfo.py`) reports the commit that `git rev-parse HEAD` returned when the server STARTED, whether the working tree is clean (measured per request) and whether the checkout moved since. When git is unavailable the commit is `null` and the UI says DESCONOCIDO. An OAF verdict is shown only when a recorded `VERDICT.json` under `logs/oaf_vertical01/*/records/<sha>/` names exactly that commit and has schema `oaf.verdict/1`; it is displayed as recorded evaluator output, never as a live evaluation and never as an acceptance.
**Operator UX.** Default source names are numbered (`Fuente 1`, `Fuente 2`, …) without duplicates (`nextLabel`). Latency, queue depth and the frame-accounting line are in a collapsed «Detalle de ingeniería» section of each feed; sampling and measured inference stay visible. The empty overview offers direct actions. The incident detail links its triggering event, says whether its source is still available (a removed feed or a deleted run produces an explicit «no disponible» state instead of a dead link) and has «Volver al monitoreo».
**Evidence.** `backend/tests/test_vertical04_state.py` (13 tests), `e2e/journey_acceptance.mjs` (the sixteen-step operator journey, isolated server), `scripts/mutation_check_v04.py` (11 mutations on a copy of the sources, clean control first, collection errors never counted as kills), `oaf/profiles/mineguard_v04.py` (DRAFT `MG-V4-OPS`).
**Limits that remain.** `STALE_OBSERVATION_S = 8` is an engineering threshold, not a validated safety value. The commit is the checkout's HEAD at server start: it does not prove the loaded modules match it if files were edited afterwards (the panel reports `tree_clean` and `checkout_moved_since_start`).

### 15.1 Snapshot policy (MG-RISK-033, MG-EVENT-033)
One rule for every response that combines the stored files of a source: take ONE immutable snapshot (`snapshot.take`), derive EVERYTHING (zones, evaluation, export bundle, retention, and the trust shown with it) from that snapshot, then compare the files on disk with the snapshot after the last read; if they moved, refuse (`409 mg.refusal.source_changed_while_read`); a missing, malformed or unsafe dependency is refused too (`409 mg.refusal.run_inconsistent`). The event cache applies the same publication rule to a HIT as to a MISS (a hit whose inputs moved is discarded and the source omitted). A zone edit that commits while a risk response is being derived therefore makes that response a refusal; the next one reflects the new revision. Trust is still computed per request, never taken from a cache, and no trust is granted by hashes alone. Cost: a hit reads the dependencies twice (snapshot and final comparison).

### 15.3 Webcam format and retention semantics (MG-WCAM-033, MG-WCAM-034)
Every session stored by this build carries `session_format = "mg.webcam.session/3"` inside its digest-bound identity (`source_digest_payload`); sessions stored before it keep their original identity. Verification adds `session_format_is_current`: without the marker a session is either LEGACY or a CURRENT one downgraded by removing members and recomputing every hash, and the two cannot be told apart by content. No canonical reference proves a historical session's format, so this is resolved fail-closed: the sample-log and accounting checks are reported as unavailable (detail text) and the session stays UNVERIFIED (no deep `verified` grant); nothing is rewritten. This changes the earlier behaviour for sessions the owner stored before this build: they now verify as unverifiable. Older accounting SHAPES remain valid for `accounting_consistent` when no current claim is made (unit-level positive controls). A current session requires the complete accounting (all STATS keys + V3 accounting).
Image hashes (`jpeg_sha256`) follow the producer: an `analyzed` sample of a Privacy-OFF (`frames`) session has one; every other sample (dropped, adapter error, client-loss stub) and every sample of a `metadata_only` session has none. The retention mode comes from the digest-bound `retention` member (absent = `frames`). No claim of external authenticity is made.
